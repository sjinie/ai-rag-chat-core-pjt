# RAG 파이프라인 설계문서 — 날씨 RAG 챗봇

선택한 지점(ASOS 관측소)의 오늘 개황을 **과거 유사 사례**와 **최근 10년 기준값**, **허용된 외부 문서**에 비추어 근거와 함께 설명한다.
용어는 `GLOSSARY.md`, 핵심 설계 결정은 `docs/adr/0001-유사사례-개황유사도.md`, 검증 수치는 `docs/검증결과.md`를 따른다.

```
[빌드]  build_climate.py ─ ASOS 일자료 10년 → SQLite(obs_daily, baseline) + Chroma station_meta
        build_forecast.py ─ 단기예보 개황 5년 → Chroma forecast_texts
        build_glossary.py ─ IPCC 용어집 PDF·기상청 용어 페이지 → Chroma climate_docs(common)

[질문]  service.ask ─ LangGraph
          retrieve: 지점 정보 + 오늘 개황(항상) → 프롬프트1 → 유사 사례(프롬프트2) / 외부 문서(수집·프롬프트2·검색) → 병합
          generate: 프롬프트3 → [근거 N] 답변 → 인용된 근거만 화면에
```

## 1. 저장소 구조와 메타데이터 필드

명세의 "항목 메타데이터 컬렉션"은 `station_meta`, "외부 문서 컬렉션"은 `climate_docs`다. 여기에 예보 문장 검색용 `forecast_texts`·`live_forecasts`와, 숫자를 임베딩하지 않고 정확히 조회하기 위한 SQLite를 더했다.

| 저장소 | 1건의 단위 | ID | 메타데이터 / 열 |
|---|---|---|---|
| Chroma `station_meta` | 지점 1곳 | 지점번호 (`108`) | `stn, name, sido, address, lat, lon, height, mountain, fct_id, office, period, source_type, title, url` |
| Chroma `forecast_texts` | 관할 지방청 × 날짜(2021~2025, 05시 발표)의 오늘 문단 | `fcst:{지방청}:{YYYYMMDD}` | `source_type, doc_id, office, date, doy, title, url, collected_at, body(원문 전체)` |
| Chroma `live_forecasts` | 오늘 개황(항목 자체 문서) | `live:{지방청}:{발표시각}` | `source_type, doc_id, office, tmfc, title, url, body, collected_at` |
| Chroma `climate_docs` | 외부 문서 청크 | `{지점}:{문서ID}:{순번}` (질문 시 수집) / `common:{ipcc\|kma_terms}:{용어}:{순번}` (고정 문서) | `source_type, stn(지점 또는 common), doc_id, title, url, query(검색어), collected_at, page(IPCC)` |
| SQLite `obs_daily` | 지점 × 날짜 관측 | `(stn, date)` | 평균·최고·최저기온, 상대습도, 평균풍속, 강수량 |
| SQLite `baseline` | 지점 × MMDD 기준값 | `(stn, mmdd)` | 6개 항목의 평균·표준편차, 표본 수, 연도 수 |
| SQLite `cache.db` | 처리 중 캐시 | `selection(stn, tmfc)`, `queries(stn, source, query)` | 유사 사례 선별 결과, 이미 수집한 검색어 |

- **지점번호를 ID로** 써서 다시 색인해도 덮어쓰기만 일어난다(F2002). 내용이 바뀐 문서만 다시 임베딩하고, 메타데이터만 바뀐 문서는 임베딩 없이 고친다(`rag/store.py upsert_changed`).
- 외부 청크 ID 앞에 **지점번호**를 붙여, 여러 지점이 같은 위키 문서를 모아도 서로 덮어쓰지 않는다(F2005). 검색은 `stn ∈ {선택 지점, common}`으로 범위를 좁힌다(F2006).
- 기준값은 공식 평년값(30년)이 아니라 **최근 10년(2016~2025) 같은 날짜 ±7일** 관측의 평균·표준편차다. 공식 평년값이 없는 대구·전주·세종·홍성까지 채우려고 대체했고, 화면과 답변에서는 "최근 10년 기준값"이라고 부른다.

## 2. 문서 수집·청킹·색인 흐름

1. **항목(지점)**: 지점 정보 API → 운영 중인 97곳. 10년 일자료로 기준값과 기후 특징(폭염·열대야·한파 일수, 연강수량, 고도 구간, 산지·섬)을 계산 → 자연어 문장으로 지점 텍스트 구성 → `station_meta`.
2. **개황(빌드)**: 관할 지방청 9곳의 5년치 개황 → "종합·오늘" 문단만 잘라(내일 이후 문장이 섞이면 다른 날과 비슷하다고 잘못 잡힘) 날짜 숫자를 지움 → `forecast_texts`.
3. **오늘 개황(질문 시)**: 관할 지방청의 가장 최근 발표분(05시 이전이나 05시분이 아직 없으면 전날 17시분) → `live_forecasts`에 항상 색인(F2004 "항목 자체 문서는 항상 색인").
4. **외부 문서(질문 시)**: 프롬프트1의 검색어 → 위키(MediaWiki 검색 API)·NASA(WordPress 검색 API)·NOAA(사이트맵 목록. robots.txt가 `/search`를 막음)에서 후보 → **프롬프트2가 제목·요약만 보고 선별**(본문을 받기 전에 버려 외부 호출을 줄임) → 본문 → 1,000자/200자 청크 → `climate_docs`. 이미 수집한 (지점, 출처, 검색어)는 건너뛴다(NF2002).
5. **고정 문서(빌드)**: IPCC AR6 WG1 용어집 PDF(용어 637개)와 기상청 특보 기준·예보용어(29개)를 **용어 하나 = 청크 하나**로 미리 색인.

외부 요청은 `rag/web.py` 하나로만 나간다. 허용 호스트 5곳 밖(리다이렉트 포함)은 막고, User-Agent에 연락처(`WIKI_CONTACT`)를 넣고, 호스트별 0.5초 간격, 429·5xx·연결 오류는 최대 4번 재시도한다(NF2006). 실패 메시지에 URL·키를 넣지 않는다(NF2004).

## 3. 검색 결과의 병합과 중복 제거

retrieve 노드가 근거를 다음 순서로 모으고, **문서 ID가 같으면 처음 것만** 남긴다(`rag/evidence.py merge`).

1. **지점 정보** — 지점 텍스트 + 오늘 지금까지의 관측을 기준값과 비교한 문장(항상)
2. **오늘 개황** — 개황 전체(항상. "그럼 내일은?" 같은 이어지는 질문에 내일 문단이 필요)
3. **유사 사례** — 프롬프트1이 필요하다고 할 때만
4. **외부 문서** — 프롬프트1이 검색어를 냈을 때만. 출처·검색어마다 순위대로 번갈아 담아 top_k개까지(한 검색어가 근거를 독차지하지 않게)

필요 없는 근거는 찾지 않는다. 예를 들어 "오늘 서울 어때?"에 프롬프트1은 외부 검색어를 내지 않으므로 위키를 검색하지 않는다(테스트 `test_no_external_search_for_today_weather`).

## 4. 프롬프트 3개 (`domain/prompts.py`)

| 프롬프트 | 역할 | 입력 | 출력 형식 | 파싱 실패 시 |
|---|---|---|---|---|
| 1 검색어 추출 | 기상청 예보관 출신 기상 전문가 | 지점, 오늘 날짜, 오늘 개황, 질문, 대화 기록 | `{"need_cases": bool, "queries": {"wiki": [], "nasa": [], "noaa": [], "ipcc": [], "kma_terms": []}}`. 위키·기상청은 한국어, NASA·NOAA·IPCC는 **영어**, 출처당 최대 2개 | "JSON만 다시" 한 번 더 → 그래도 실패하면 지점 정보·오늘 개황만으로 답 |
| 2 후보 선별 | 기상 전문가 | 번호·제목·요약 목록과 기준 문장. 용도 3가지: 유사 사례(오늘 개황과 현상·시간대가 맞는가), 외부 문서(질문에 쓸 만한가), 조건 탐색(조건에 맞는 지점인가) | `{"selected": [번호]}` | 한 번 더 → 실패하면 선택 없음(캐시·검색어 기록 안 함, 다음에 다시 시도) |
| 3 답변 생성 | 기상청 예보관 출신 기상 전문가 | 근거 블록 `[근거 N] (유형) 제목\n본문`, 질문, 대화 기록 | 한국어 답변. 주장마다 `[근거 N]`, 근거에 없으면 "근거 문서에서 확인되지 않습니다.", 숫자는 근거의 값만(새로 계산 금지), "평년값" 대신 "최근 10년 기준값", 유사 사례는 예보가 아님을 밝힘 | — |

**숫자 계산은 LLM에 맡기지 않는다.** 기준값과의 차이, "매우 낮음~매우 높음" 판정(z = 차이/표준편차, ±1·±2 경계)은 코드(`domain/stations.py`)가 계산해 문장으로 넘긴다.

모델은 프롬프트 3개와 단순 채팅 모두 `gpt-6-luna`(SSAFY GMS), 임베딩은 `text-embedding-3-small`.

## 5. 청크 크기·중복 길이·Top-k

| 값 | 설정 | 고른 이유 | 바꿨을 때 |
|---|---|---|---|
| 청크 크기 / 중복 | 1,000자 / 200자 | 명세 시작값. 위키 한 절이 대체로 1,000자 안팎이라 문단이 덜 잘림 | 500자로 줄이면 같은 2,400자 문서의 청크 수가 늘어남(테스트 `test_chunk_size_from_config`) |
| top_k | 4 | 출처가 5곳이라 4개면 대체로 출처마다 1순위가 하나씩 들어감 | 대표 질문 ⑤: top_k=2면 한국어 출처 둘(위키)만, 4면 NASA·IPCC 추가, 8이면 같은 출처의 2순위 청크가 섞임 |
| 검색 방식 | similarity (`mmr` 전환 가능) | 출처·검색어별로 번갈아 담기가 이미 다양성을 줌 | 검색어 하나일 때 MMR은 4개 중 3개를 다른 청크로 바꿈(`docs/검증결과.md` MMR 비교) |
| 유사 사례 후보 / 최대 | 10 / 5 | 프롬프트2가 고를 여유를 두되 문맥을 과하게 늘리지 않음 | — |

## 6. 근거 표시 방식 (F2008)

- 답변 본문의 `[근거 3]`, `[근거 1, 3]` 표기를 찾아 **실제로 인용된 근거만** 화면에 남긴다(없는 번호는 무시). 근거마다 `제목 · 유형 · [원문](URL)`.
- 유형은 항목(지점 정보·오늘 개황·유사 사례)과 외부 문서(위키백과·NASA·NOAA·IPCC 용어집·기상청 용어·기준)로 나뉜다(F2007, F2016).
- 인용이 0건이면 "ⓘ 답변에 인용된 근거가 없습니다.", 유사 사례가 문맥에 있으면 "과거 유사 사례는 참고용이며 예보가 아닙니다.", 모든 답에 "공식 특보·예보는 기상청 발표를 확인하세요."
- API 주소에는 키가 들어 있어 원문 링크로 쓸 수 없다. 관측·지점 정보는 기상자료개방포털 ASOS 페이지, 개황은 API허브 첫 화면을 링크한다(과거 개황마다 열어 볼 공개 주소는 찾지 못함).

## 7. 도메인 특화 기능: 과거 유사 사례 (F2010, ADR 0001)

텍스트 임베딩은 "14.1℃"와 "14.3℃"가 가깝다는 것을 모른다. 그래서 숫자를 임베딩하지 않고, **사람이 쓴 예보 문장끼리** 비교한다.

1. 오늘 개황의 오늘 문단으로 **같은 관할 지방청**의 과거 개황 중 비슷한 날을 찾는다(날짜 조건 없음. 다른 지방청 개황은 다른 지역 이야기라 선택 지점의 답이 되지 못함).
2. 그날 **선택 지점의 실제 관측**을 SQLite에서 조회하고, **그날 기준값과의 차이**로 바꾼다(다른 계절의 날이 뽑혀도 "평소보다 추웠다"는 비교가 성립).
3. 관측이 없는 날은 빼고 다음 순위로 10건을 채우고, 프롬프트2가 현상·시간대가 맞는 사례만 고른다.

사후 검증(2025년 지방청별 30일, 270일): 사례들의 편차를 오늘 기준값에 더한 최고기온 오차는 **2.53℃로 기준값만 쓴 3.11℃보다 작고**, 비 온 날 맞힘은 **87%로 '항상 비 없음' 76%보다 높다**. 원값 그대로 평균하면 계절이 섞여 3.69℃로 오히려 나빠서, 화면에 편차로 보여 주는 설계(2번)가 필요함이 확인됐다.

"오늘 날씨 리포트" 버튼은 같은 근거로 6개 항목 비교표와 해설을 보여 준다.

## 8. 출처별로 수집·청킹을 달리한 이유 (F2016)

| 출처 | 수집 | 청킹 | 이유 |
|---|---|---|---|
| 위키·NASA·NOAA | 질문할 때 검색·선별·수집 | 1,000자 / 200자 | 문서가 많고 길어서 필요한 것만 그때 받는다 |
| IPCC 용어집, 기상청 특보 기준·예보용어 | 빌드 때 한 번 | 용어 하나 = 청크 하나 | 고정된 문서 하나라 질문마다 받을 이유가 없다. 1,000자로 자르면 한 청크에 정의가 여러 개 섞이거나 한 정의가 둘로 갈라진다. PDF는 굵은 글꼴(BlackCn)로 용어 시작을, 기상청 페이지는 HTML 표의 첫 칸으로 용어를 찾는다 |
| 기상청 개황 | API(빌드 5년치 + 질문 시 오늘) | 오늘 문단 하나 = 1건 | 문장 유사도로 날짜를 찾는 용도라 자르지 않는다 |

## 9. 겪은 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 대관령 1월 최저기온 기준값이 -5.6℃로 따뜻하게 나옴 | 결측 표시(-9)를 "−9 이하는 결측"으로 처리해 실제 영하 기온을 버림 | 기온 결측은 -99.0만, 습도·풍속은 -9.0. 실제 행(-20.9℃)으로 테스트 → -11.8℃ |
| 오류 메시지에 API 키 노출 | requests 예외 메시지에 키가 든 URL 전체가 들어감 | 예외를 종류 이름만 남겨 다시 던지고 재시도 |
| 개황 원문 디코딩 실패 | EUC-KR 밖의 한글 | `cp949`로 읽음 |
| 지점 정보 일부 행의 열이 밀림 | 영문명에 공백("Jeongseon Gun") | 예보구역코드는 모양으로, 주소는 첫 한글 단어부터 찾음 |
